# chibitv_ffmpeg

Video transcoding for chibitv on a minimal FFmpeg, bound through
[rsmpeg](https://github.com/larksuite/rsmpeg).

MPEG-2 or HEVC goes in, H.264, HEVC or AV1 comes out, deinterlaced on the way
where broadcast video needs it. A stream already in the codec asked for passes
through untouched. Nothing of FFmpeg shows in the API: callers name codecs,
accelerations and access units, and the timestamps are seconds like elsewhere
in chibitv.

```rust
use chibitv_ffmpeg::{Deinterlace, Transcoder, TranscodeOptions, VideoCodec};

let mut options = TranscodeOptions::new(VideoCodec::H264);
options.deinterlace = Deinterlace::Frame;
let mut transcoder = Transcoder::new(VideoCodec::Mpeg2, options)?;

for packet in access_units {
    transcoder.push(packet)?;
    while let Some(output) = transcoder.pull() {
        // An H.264 access unit in Annex B, parameter sets at every keyframe.
    }
}
transcoder.finish()?;
while let Some(output) = transcoder.pull() {
    // What the encoder held back.
}
```

## Building FFmpeg

FFmpeg is built and installed by `build.sh`, with nothing but what the
backends named to it need:

```shell
crates/chibitv_ffmpeg/build.sh software vaapi
```

It fetches the release archive, configures it, builds it as static libraries
and installs them under `vendor/` next to the script, which Git and Docker
ignore. The workspace's `.cargo/config.toml` points rusty_ffmpeg, the
bindings under rsmpeg, at that install through `FFMPEG_PKG_CONFIG_PATH`, and
the crate's `build.rs` reads what the script built so that a Cargo feature
whose backend is missing fails the build with the command to run.

This is a step of its own rather than part of `cargo build` because the
bindings are generated by a dependency's build script, which runs before this
crate's own could build anything.

The script needs `make`, a C compiler, `nasm` (on x86; the build works without
it but is slow), `curl`, `tar` and `pkg-config`, plus the development package
of each library a backend links. The Rust build then needs `libclang` for
bindgen. Environment variables:

- `CHIBITV_FFMPEG_VENDOR_DIR`: put `vendor/` elsewhere, for instance in a cache; then set `FFMPEG_PKG_CONFIG_PATH` to its `prefix/lib/pkgconfig` for cargo too.
- `CHIBITV_FFMPEG_SOURCE`: an FFmpeg source tree to build instead of the release archive.
- `CHIBITV_FFMPEG_AMF_INCLUDE`: the directory holding `AMF/` for the `amf` backend.

Only Linux and macOS builds have been exercised. Windows needs an MSYS2 shell
in an MSVC developer environment, since FFmpeg's `configure` is a shell script.

## Backends and features

Each backend is both an argument to `build.sh` and a Cargo feature: the script
puts it into FFmpeg, the feature says the crate relies on it. Without any
feature the crate has no FFmpeg at all and can only pass streams through, so
the rest of the workspace builds without any of the dependencies below.

| Backend        | What it adds                                        | Platforms       | Build dependency                                           |
| -------------- | --------------------------------------------------- | --------------- | ---------------------------------------------------------- |
| `videotoolbox` | Apple VideoToolbox decode, deinterlace and encode   | macOS           | none                                                       |
| `nvidia`       | NVIDIA CUVID decode with deinterlace, NVENC encode  | Linux, Windows  | `ffnvcodec` headers (`nv-codec-headers`)                   |
| `qsv`          | Intel Quick Sync decode, deinterlace and encode     | Linux, Windows  | `libvpl-dev` (and `libva-dev` on Linux)                    |
| `vaapi`        | VA-API decode, deinterlace and encode               | Linux           | `libva-dev`                                                |
| `amf`          | AMD AMF encode after a software decode              | Windows, Linux  | AMF SDK headers, pointed at with `CHIBITV_FFMPEG_AMF_INCLUDE` |
| `x264`         | H.264 software encode (GPL)                         | all             | `libx264-dev`                                              |
| `x265`         | HEVC software encode (GPL)                          | all             | `libx265-dev`                                              |
| `svt-av1`      | AV1 software encode                                 | all             | `libsvtav1enc-dev`                                         |
| `software`     | `x264`, `x265` and `svt-av1`                        |                 |                                                            |

`build.sh` also takes `mpeg2-encoder`, which the tests make their input with.

A hardware backend only exists on the platforms in its row and is skipped
with a warning elsewhere, by the script and the features alike, so one list
serves every platform. `Acceleration::available()` reports what the FFmpeg
linked in has; whether the machine has the hardware is found out when a
`Transcoder` opens, which tries the accelerations in order and falls back to
the next when one does not work.

## Layout

- `build.sh`: builds and installs FFmpeg with the backends named to it.
- `build.rs`: turns what the script built into `cfg`s and checks the features against it.
- `src/av.rs`: the only module using rsmpeg and FFmpeg's API; decoders, filter graphs and encoders on one 90 kHz clock.
- `src/backend.rs`: what each acceleration decodes, filters and encodes with, and the options it takes. Pure, and tested on its own.
- `src/pipeline.rs`: the decode, filter, encode chain, and the search for an acceleration that works here.
- `src/lib.rs`: the public API.
